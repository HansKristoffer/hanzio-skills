# Our libraries

Hans Kristoffer maintains a set of npm packages (all `HansKristoffer/<repo>` on GitHub) that hold the generic code our apps used to copy between each other: hellu (the template every new project is copied from, oRPC backend), gey-mono and budget-app. This skill tells you which package covers which need, what local code it replaces, and how to adopt it without breaking the app.

Two rules shaped every package, and they decide what you adopt:

- **Thin layer over the native library.** Each package ships configuration, defaults and the glue every app rewrote, on top of the real library (oRPC, Mastra and the AI SDK, graphile-worker, Hono, TanStack Router, Bun Redis). Routers, agents, memory, queues and the database stay the native library's. When a package and its peer disagree, the peer's docs win.
- **No domain code.** Auth (Better Auth wiring, impersonation, permissions), feature flags, messages (email/SMS/Slack), logging/OTel/PostHog setup and the Biome/tsconfig presets were **dropped on purpose** (better-saas, better-observe and dev-config were closed). That code stays in the hellu template and is copied with it. Do not look for a package for it, and do not propose extracting it.

## Process

1. **Read the target repo first.** Root and nearest `AGENTS.md` / `CLAUDE.md` (their rules win over this skill), the root `package.json` (workspaces, catalog, scripts, `packageManager`), each app's `package.json`, and the runtime (Bun or Node, and which version). List which of our packages are already installed and at what version; compare with `npm view <pkg> version`. A repo on an old major (for example gey-mono on `hanzio ^2`) needs the upgrade before anything else.
2. **Find candidates.** For each package that could apply, grep the repo for its symptoms under **What it replaces**. A candidate is local code that does what a package export does; note its path and rough line count. Code that only looks similar but carries domain rules stays.
3. **Match needs to packages** with the table below. Respect the hard limits: Bun-only packages in a Node app, Zod 3, Postgres-only, tRPC backends (orpc-fn needs oRPC), Mastra or AI SDK below the peer range.
4. **Propose an adoption plan before editing.** One row per package: what it replaces (paths + lines), what it adds, the peers to install, the order, and what you leave alone and why. Order by dependency: hanzio first (others depend on it), then buncargo (the commands you verify with), then backend (orpc-fn, better-graphile-worker, hono-webhooks, measurr), then AI (better-mastra, decision-api, website-to-markdown), then clients (orpc-fn `/vue` `/react`, tanstack-router-sfc, expo-release). One package per commit or PR, so a regression points at one swap. Wait for approval when the plan deletes code or changes behaviour.
5. **Adopt one package at a time.** Install it with the peers its `package.json` declares, follow its README setup, move each call site to the package export, then **delete** the local copy. If the package lacks a behaviour the local code had, keep the app working and write it up as a library follow-up (file, missing behaviour, suggested fix) instead of silently re-adding a local copy. Run the repo's full checks (lint, typecheck, tests) after each package.

For a **new project**, skip step 2: start from the hellu template (`~/Documents/GitHub/hellu`), which already wires most packages, and use the recommended stack below for whatever the template lacks.

## What it replaces

Grep for these when looking for adoption candidates. A hit is a candidate, not a verdict: code carrying domain rules stays.

- **hanzio:** `import Redis from 'ioredis'` singletons; `setInterval` writing SSE keep-alive comments; hand-rolled `parseArgs` bins with a `USAGE` string or `trpc-cli`, or shims around `cli.run()` that prepend a default command or remap exit code 2; per-app `.env`/`getSecret` loaders or `infisical run --` wrappers; local i18n parity/type scripts or `bun --bun x hanzio-i18n`; `formatDate`/`formatCurrency`/country-currency mapping copies; `fetch` wrappers with zod parsing and retry loops; `assertNever`, `Result`, `groupBy`, `debounce`, `slugify` copies; `satisfies` casts on `typedSwitch` cases; a local `secret-json` sealer (`createCipheriv('aes-256-gcm'`); `mock.module` helpers, a `ModuleMocker` subclass, `as unknown as` casts on Prisma mocks; hand-written wait/queue-depth metrics around the Redis limiter.
- **orpc-fn:** a local `fn()` wrapper adding spans, guards and logs around `os.handler(`; hand-built `new RPCHandler(`/`OpenAPIHandler` mounting on Hono; `redis.publish(` next to `subscribe(` in API code; per-domain change buses and a shell stream fanning them in; change buses passing `inputSchema: z.object({})` or building channel names by hand (`` `${prefix}:${organizationId}` `` before `backlogKey(`); client subscription composables with `reconnectDelay` or `document.visibilityState`; `ReturnType<typeof useApiClient<…>>` or `as` casts on query composables; hand-written Mastra/MCP tool wrappers calling a procedure; scripts that call backend services directly.
- **better-mastra:** per-provider LLM route files (OpenRouter, Vertex, Anthropic/OpenAI direct), cost tables, Mastra storage/memory setup with DDL retries, a hand-written chat turn and chat route, a chat run aborted by `request.signal`, local chat client hooks; per-user rate limits from Redis `INCR` + `EXPIRE`; an Upstash polling loop for resumable chat; a cron deleting abandoned Mastra runs; `visibilitychange`/`online`/`AppState`/NetInfo listeners that reconnect a chat stream; a hand-generated tool manifest type.
- **better-graphile-worker:** `from 'graphile-worker'` outside one queue module; `addJob(`/`quickAddJob(` with untyped payloads; one `run({ concurrency })` per lane; `localQueue: { size: … }` per runner; `JSON.parse(JSON.stringify(` before enqueue; `prepareJob` + `$queryRawUnsafe` inside a Prisma transaction, or a transactional-enqueue wrapper with `task as never`/`payload as never` casts; hand-written `graphile_job_*` metrics or metric-catalog entries; Trigger.dev tasks (`@trigger.dev/sdk`, `schedules.task`).
- **measurr:** a `lib/metrics` engine with `defineKpiMetric`-style factories or a hand-written metric registry (key → resolver map, per-metric filter parsing, previous-period alignment); presenters turning rows into KPI/timeseries/donut/leaderboard payloads; `prisma.<model>.groupBy(` in metric resolvers; hand-written `date_trunc`/`AT TIME ZONE` (Postgres) or `toStartOfDay`/`query_params` (ClickHouse) dashboard SQL; numbers stitched from two databases after the query; tenant ids threaded into every query; imports of `metrickit` or `ts-metrics`.
- **buncargo:** `scripts/check.ts`, `typecheck-ci.ts`, `pre-deploy.ts`, `ensure-docker.sh`; a script checking Markdown links or backticked repo paths in docs; a `docker-compose.yml` with fixed ports; per-worktree `.env` port juggling; `concurrently`/`turbo dev` dev scripts; Vite configs hard-coding `server.port`, `allowedHosts` or an `/api` proxy. Not covered: `predeploy` migrates with the deploy's own `DATABASE_URL` and never reads `DATABASE_URL_DIRECT`; keep that switch in the Railway command (`DATABASE_URL=$DATABASE_URL_DIRECT bunx buncargo predeploy`).
- **expo-release:** `Updates.checkForUpdateAsync()` + `reloadAsync()` in a `useEffect`; a `NotificationService` class; hand-rolled `addPushTokenListener`/`getExpoPushTokenAsync` re-registration; an optimistic push-preference toggle with manual rollback; a class `ErrorBoundary`; workflow steps running `eas fingerprint:generate`, `eas build:list` or `eas update --branch`; hand-written PR preview database/DNS workflows; local setup/install/Playwright-cache actions with self-hosted runner tweaks; a changelog workflow curling an LLM API.
- **hono-webhooks:** `createHmac(` + `timingSafeEqual` against `x-hub-signature-256`, `x-shopify-hmac-sha256`, `stripe-signature` or `svix-signature`; Stripe `constructEvent`; `app.post('/webhooks/...')` routes parsing the body themselves; hand-written webhook spans/metrics, `webhook_request_*` entries in a metric catalog, or a per-request webhook completion log.
- **tanstack-router-sfc:** `x.ts` + `x.component.vue` route pairs; `createVueRouterShim`; local `useRouteSearch`, `useDialog`, route-loading and form composables; a `patches/tanstack-router-sfc@*` patch.
- **website-to-markdown:** Cloudflare `toMarkdown`/Browser Rendering calls; Turndown/Readability pipelines; hand-rolled robots.txt or `<loc>` regex parsers; a private-IP check before fetching user URLs; app wrappers around `createWebsiteToMarkdown` that filter Workers AI timeouts out of error tracking or bind crawl snapshots; a crawl-snapshot name regex copied into a shared schema.
- **decision-api:** an LLM structured-output call whose schema is only a boolean or a `z.enum`, used to tag, route, gate or rank. Keep text fields on a generation model; only the decision moves.
- **plantr:** a `prisma/seed.ts` with a profile parser, long hand-ordered seed files, manual seed-phase progress logging, `"prisma": { "seed" }` scripts.
- **taurio:** a Tauri app calling `check()`/`downloadAndInstall`/`relaunch` from the updater and process plugins itself, `ask(` dialogs, or per-window vibrancy code in `lib.rs`.

## How they fit together

- **hanzio is the base.** orpc-fn, better-mastra and expo-release depend on `hanzio ^3.3`, website-to-markdown peers on `^3.3` and buncargo pins `3.3.0` for its CLI. Bring the app to hanzio 3.3 before adopting any of them. Keep the app's own `hanzio` on the same major so types like the CLI `CommandGroup` come from one copy.
- **App CLI = orpc-fn procedures + hanzio/cli.** Mark procedures `meta: { cli: true }`, then `defineCli({ ..., commands: procedureCommands(router, { context }) })`. Each command runs through oRPC, so guards, tracing and logs behave as over HTTP. Run it with the app's env through buncargo (hellu: `bunx buncargo exec --app=api -- bun apps/backend/src/entry/cli.ts`). Library bins (orpc-fn, better-mastra, expo-release, hono-webhooks, website-to-markdown, buncargo) are built on `hanzio/cli` too; better-graphile-worker's `createCli` still uses `parseArgs`.
- **One procedure, many surfaces.** A `fn()` procedure is the HTTP route (`mountOrpc`), a live query (`fnLive`), an agent tool (`orpc-fn/mastra` `createMastraTool`, then better-mastra `defineTool({ tool, tier })` for tier, card and manifest), an MCP tool (`orpc-fn/mcp/*`) and a CLI command. Install `@mastra/core` at better-mastra's range (^1.76); it also satisfies orpc-fn's ^1.51.
- **Realtime.** Server: `fnLive` per query, `defineScopedChangeBus` per domain (scoped by organization; `bus.channelFor(scope)` gives the full channel name, e.g. for `backlogKey`), one `invalidationStream` procedure for the app shell. Client: `orpc-fn/vue` or `/react` `useLiveQuery` and `useInvalidationStream`; type Vue query helpers with `orpc-fn/vue`'s `ApiClient`, not `ReturnType<typeof useApiClient<…>>`. Generate the stream manifest with `orpc-fn stream-manifest` and run it with `--check` in CI, or streams get batched and break.
- **Writes, jobs and events.** Write and enqueue in one Prisma transaction with the worker's (or pool's, or job client's) typed `enqueueInTransaction(tx, { task, payload })`, then publish the orpc-fn change event after commit. Run long or retryable work (AI turns in hellu's support agent, crawls, imports) as typed queues; give slow queues their own runner in a `createBetterWorkerPool` so they do not hold the workers fast queues need, and set `prefetch` on the pool or per runner.
- **AI assistant.** better-mastra owns models (`/models`, `/openrouter`), storage (`/pg` or `/libsql`; the root storage exports are deprecated), memory, per-user request limits (`/usage`), the turn, the Hono chat route and the clients. decision-api runs beside it for typed judgments (outside the Mastra model factory). website-to-markdown feeds knowledge. measurr's `querySchema` and `analyticsToolGuidance` make a ready analytics tool.
- **Redis.** Use Bun's client throughout: `hanzio/redis` (`createManagedRedis`, `createRedisConcurrencyLimit` with metric hooks, which website-to-markdown's `createLimit` accepts to share a quota across processes), orpc-fn `/live/redis-bun`, better-mastra `/resumable` `bunRedis` (`upstashRedis` on Upstash).
- **One Hono app, one OTel API.** `mountOrpc`, hono-webhooks, better-mastra's chat route and Studio mount on the same Hono app. Pass the same `@opentelemetry/api` to `createFn({ otel })`, better-graphile-worker (`otel: { api, metrics: true }`) and hono-webhooks `/otel`; spread `queueMetricDefinitions` and `webhookMetrics` into the app's metric catalog instead of redeclaring them. The OTel/PostHog setup itself stays in the app.
- **Tooling.** buncargo's `dev.config.ts` drives dev, `check` (pre-commit `--staged`), `typecheck`, `ci`, Prisma and Railway `predeploy`; seeds run plantr through `seed: { command }` (`predeploy.seed` gives deploys their own command, or `false`); its Infisical fetch matches `hanzio/secrets`, so the app finds secrets in `process.env`. expo-release ships the Expo app; its `setup-workspace` action and buncargo's setup action both install Bun, so pick one per workflow.
- **Clients.** Vue platform: tanstack-router-sfc + its `/app` kit, `orpc-fn/vue`, `hanzio/i18n/vue`, `better-mastra/vue`. Expo: `orpc-fn/expo` `createBetterAuthExpoLink` (with `normalizeExpoOrigin` in `mountOrpc` on the server), `orpc-fn/react`, `better-mastra/react`, `expo-release/runtime`, `hanzio/i18n/i18next`.

## Recommended stack for a new hellu-style project

Bun monorepo, `apps/backend` (Hono + oRPC + Prisma 7 on Postgres + Better Auth + graphile-worker + Mastra), `apps/platform` (Vue + TanStack Router + Nuxt UI), `apps/expo` (Expo Router), `packages/prisma`.

| Area | Use |
| --- | --- |
| Dev environment, checks, deploy | buncargo (`dev.config.ts`, `check`, `typecheck`, `predeploy`), plantr seeds |
| Helpers, secrets, Redis, i18n, CLI | hanzio (`/secrets`, `/redis`, `/http`, i18n + `hanzio-i18n check` in CI, `/cli`, `/format`, `/iso`, `/api-wrapper` for third-party APIs) |
| API and realtime | orpc-fn (`createFn` in `lib/fn`, `mountOrpc`, `fnLive`, change buses, `invalidationStream`, stream manifest in CI) |
| Jobs and cron | better-graphile-worker (pools with lanes and `prefetch`, typed `enqueueInTransaction`) |
| Inbound webhooks | hono-webhooks (+ `/otel`) |
| Analytics and dashboards | measurr (`/metrics` registry behind one batched procedure, `/shapes` on the client) |
| AI assistant | better-mastra; decision-api for typed judgments; website-to-markdown for website knowledge |
| Web frontend | tanstack-router-sfc (+ `/app`), `orpc-fn/vue`, `better-mastra/vue` |
| Mobile | `orpc-fn/expo` + `/react`, `better-mastra/react`, expo-release (action + `/runtime`) |
| Stays in the template | Better Auth setup, permissions, feature flags, messages, logging/OTel/PostHog, Biome/tsconfig presets, all domain features |

Only add what the project needs now: a project with no assistant skips better-mastra, one with no mobile app skips expo-release.

## Keeping this skill current

When a package releases, re-check its row and replace line against the published `.d.ts` and CHANGELOG and bump the version after its name. API details live in each repo's README. A new package (check `npm search maintainer:hanskristoffer`) gets a table row and a replace line. If this skill and a package README disagree, the README wins; fix the row.
